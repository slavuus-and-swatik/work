# FORMA — первый шаблон детейлинга

## Работа в студии

1. Открыть `/studio`, войти паролем команды, создать проект с уникальным адресом.
2. Вкладки «Дизайн», «Услуги», «Контент», «Запуск»: настроить бренд, фото, тексты, прайс и длительности, расписание и число постов, контакты. Референсы сохраняются как ссылки; их содержимое не импортируется автоматически.
3. «Сохранить» → «На согласование» → вкладка «Запуск» → скопировать ссылку `/review/<token>`. Отправить клиенту вручную. Клиент видит тот же компонент сайта и форму записи в режиме предпросмотра.
4. Клиент нажимает «Оставить ответ»: согласовать или запросить правки с комментарием. В студии ответ обновляется при возвращении в окно и каждые 15 секунд, если нет несохранённых правок.
5. После согласования нажать «Опубликовать сайт». Адрес `/s/<slug>`. Любые новые изменения остаются черновиком до нового согласования и публикации. Старые ссылки показывают свою версию, но не принимают повторный ответ.
6. Для настоящих записей отключить демонстрацию и заполнить телефон, адрес, оператора и условия обработки данных. Новые проекты создаются в деморежиме; цены и название примерные, обложка сгенерирована. Реальные работы добавляются самостоятельно.
7. Заявки находятся во вкладке «Заявки» соответствующего проекта. До подтверждения связаться с клиентом. Новая заявка резервирует время; отмена освобождает его. Отменённую запись нельзя восстановить поверх другой записи.

## Устройство и ограничения первой версии

Общий компонент `components/detailing/site.tsx` используется для редактора, согласования и публикации. Согласование хранит неизменяемую копию конфигурации. Публикация разрешена только для согласованной текущей версии. Оптимистичная проверка версии защищает от перезаписи из другой вкладки.

SQLite в режиме WAL хранит проекты, снимки, записи и загруженные изображения. Запись и выбор свободного поста проходят в одной `BEGIN IMMEDIATE` транзакции. Данные сохраняются после перезапуска процесса. Одна база на одном VPS; для нескольких независимых серверов приложений потребуется общая база и объектное хранилище. Часовой пояс расписания — Москва, горизонт записи 90 дней, шаг 30 минут, не менее часа до визита.

Вход команды общий, отдельные кабинеты владельцев и роли не добавлены. Письма, Telegram-уведомления, платежи, персональные домены, автоматическое подключение аналитики не подключены. Ссылки согласования доступны каждому, кто получил ссылку: их следует отправлять только нужному клиенту. Получение ответа не отправляет сайт в интернет автоматически.

## Запуск

Node.js 24+, pnpm, переменные окружения:

- `DETAILING_DATA_DIR`: постоянный каталог, например `/var/lib/detailing`, вне каталога релиза.
- `APP_ORIGIN`: единственный публичный HTTPS origin без завершающего слеша.
- `PLATFORM_AUTH_SECRET`: случайный секрет минимум 32 байта.
- `PLATFORM_ADMIN_PASSWORD_HASH_B64`: base64 от bcrypt-хеша 32-символьного пароля команды. Хранить только на сервере, не в Git.

`pnpm install --frozen-lockfile`, `pnpm build`. Для standalone-релиза скопировать `.next/standalone`, `.next/static` в `.next/static` релиза, нужные `public`-файлы и `deploy/`. Нативные зависимости собирать на целевой ОС/архитектуре. Для внешнего доступа использовать HTTPS и Nginx; Node слушает только 127.0.0.1:3017. Шаблон `deploy/nginx-location.conf` допускает только новые маршруты. Он специально не открывает старые демонстрационные API магазина, `/admin`, архив исходников и Next Image Optimization.

Перед заменой работающего приложения проверить существующие systemd/Nginx настройки и данные. Сохранить предыдущий релиз и конфигурацию. Переключать `/opt/detailing/current` только после успешной сборки, проверки приложения и `nginx -t`. Откат: вернуть ссылку на предыдущий релиз и перезапустить service; постоянную базу не удалять.

`deploy/detailing.service` запускает приложение непривилегированным пользователем. `deploy/detailing-backup.timer` вызывает Python SQLite backup ежедневно. Копии содержат изображения и данные заявок; нужны закрытый доступ и отдельная копия вне VPS. Удаление старых бэкапов пока ручное. Проверка восстановления: восстановить копию в отдельный каталог, выполнить `PRAGMA integrity_check`, запустить отдельный процесс с этим `DETAILING_DATA_DIR`; не восстанавливать поверх работающей базы.

## Проверка

`pnpm build` проверяет TypeScript и production-сборку. `node scripts/detailing-smoke.mjs` поднимает отдельный процесс с временной базой и проверяет вход, чужой origin, неопубликованные изменения, устаревшие версии, согласование и правки, публикацию, одновременную запись, изоляцию проектов, сохранность после рестарта, отмену и снятие с публикации. Тест не использует настоящие клиентские данные. `--keep` оставляет QA-сервер для ручной проверки. Доступ к нему сохранён в `access.json` временного каталога с правами 0600.

Next.js обновлён с 16.4.0 до 16.4.3 после предупреждения сборщика. Официальное описание исправлений: https://nextjs.org/blog/nextjs-security-update-october-14-2026

## Обложка

`public/detailing-hero.png` — изображение, созданное встроенным imagegen для демонстрационного шаблона, не фотография работы клиента. Направление промпта: фотореалистичный широкий кадр, тёмный графитовый автомобиль купе без логотипов, задний ракурс три четверти справа в спокойном детейлинг-боксе, белые полосы света в отражениях, слева тёмное свободное пространство для заголовка; без текста, неона и чужих брендов. При продаже заменить на согласованный клиентом материал.
